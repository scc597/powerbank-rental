## 一、实验目的

1. 理解边界值分析法及健壮边界值分析法的基本原理和适用场景。
2. 能够针对具有明确输入范围的软件功能设计边界值测试用例，并完成测试执行、结果记录与分析。
3. 能够比较不同边界值测试方法在测试用例设计上的差异，理解不同测试策略的特点。
4. 培养小组成员之间的任务分工、协作测试、结果讨论和问题分析能力。

**本次实验的达成情况**：四项目的全部达成。其中第 3 项目标通过"两种方法的对照实验"完成，

### 2.3 核心业务规则（多条件）

**费用计算规则**（按顺序判定，任一命中即短路）：

```
输入：租借时长 minutes、会员等级 level、是否用券 useCoupon

1. 免费段     minutes ≤ 60                       → 0.50（最低消费）
2. 阶梯计费   60 < minutes ≤ 600                 → (minutes−60) × 0.10
              minutes > 600                     → 54.00 + (minutes−600) × 0.08
3. 费用封顶   阶梯费用 > 60.00                   → 60.00
4. 会员折扣   普通 1.00 / 银卡 0.98 / 金卡 0.95 / 黑钻 0.90
5. 优惠券     折后 ≥ 5.00 且用券                 → 再减 2.00
6. 最低消费   最终 < 0.50                       → 0.50

总费用 = 单台费用 × 租借数量（保留 2 位小数）
```

该规则链包含 **5 个可测边界点**：免费时长 60、阶梯切换 600、费用封顶 60 元、
优惠券门槛 5 元、最低消费 0.5 元，是本系统边界值测试的核心目标。

### 2.4 数据流分析（变量定义—赋值—使用）

以 `RentalOrder.calcUnitFee()` 为例：

| 步骤 | 变量 | 定义 | 赋值 | 使用 |

| 1 | `chargeable` | 定义 | `useMinutes − 60` | 判空、早退分支 |
| 2 | `tierFee` | 定义 | 阶梯公式（2 个分支） | 封顶比较 |
| 3 | `tierFee` | — | `tierFee × 折扣率` | 优惠券门槛比较 |

## 三、测试用例设计

### 3.1 两种方法的原理

| 方法 | 取点规则 | 每个输入域点数 |
|------|---------|--------------|
| **正常边界值分析法** | 下界、下界+1、有效内点、上界−1、上界 | 5 |
| **健壮边界值分析法** | 下界、下界+1、有效内点、上界−1、上界、**下界−1、上界+1** | 7 |

健壮边界值法在正常边界值的基础上向无效区间多取一个值，用于检验系统的**健壮性**——
无效输入必须被拒绝，而不是崩溃或错误接受。

| **合计** | | **141** |

## 四、两种边界值测试方法的对比

| 对比维度 | 正常边界值分析法 | 健壮边界值分析法 |
|---------|----------------|----------------|
| **取点数量** | 每输入域 5 点 | 每输入域 7 点 |
| **取值范围** | 全部落在有效区间内 | 含 2 个无效区间点 |
| **覆盖的输入域** | 年龄、充值金额、信用分（3 类数值域） | 年龄、充值金额、信用分、手机号（新增 3 类格式/唯一性域） |
| **数值型输入点** | 22 个 | 19 个 |
| **用例总数** | 39 | 39 |
| **异常输入覆盖** | 部分（仅覆盖紧邻越界点） | 充分（含极端值、null、空串、重复值） |
| **发现缺陷** | 未发现被测程序缺陷 | **发现 DEF-01（严重）** |
| **执行耗时** | 0.051 s | 0.048 s |

### 4.1 差异分析

**（1）取值范围**

正常边界值法聚焦"边界内侧的功能是否正确"，其数据点全部落在有效区间内，
适合验证功能的**正确性**。健壮边界值法则越过了边界进入无效区间，
验证的是系统的**防御能力**。本系统中，年龄 17 岁这一数据点在方法一中
仅作为"附带断言"存在（TC-MB-02），而在方法二中它是**独立的核心测试点**（TC-MR-02），
并配套验证了"拒绝后系统状态保持干净"这一健壮性要求。

**（2）异常输入覆盖**

方法一的异常覆盖是"浅"的——只测下界−1 和上界+1。
方法二在此基础上大幅扩展：

| 扩展类型 | 方法一 | 方法二 |
|---------|-------|-------|
| 极端值 | 无 | `Integer.MIN_VALUE`/`MAX_VALUE` |
| 空引用 | 无 | 手机号 null、姓名 null |
| 空字符串 | 无 | 姓名为 `"   "` |
| 唯一性冲突 | 无 | 同一手机号重复注册 |
| 累积越界 | 无 | 累计充值恰好 20000 / 超出至 20001 |
| 状态回滚校验 | 部分 | 每条拒绝用例后均断言原状态未变 |

**（3）缺陷发现能力**

方法一的 39 条用例**全部通过**，未发现被测程序缺陷。
方法二则在交互层发现了 DEF-01（详见第五节）。

这一对比印证了一个重要结论：**正常边界值法能发现"计算错误"，健壮边界值法能发现"遗漏的分支处理"**。
本次发现的 DEF-01 正是典型的"遗漏空输入分支"——它在有效区间内不可能暴露，
只有在主动输入无效值时才会显现。

### 5.3 TCX-01 分析：费用封顶边界预期值错误

**现象**

```
TC-FB-03 feeCapBoundary 失败
AssertionFailedError: 预期金额 60.0，实际 55.2
```

**分析过程**

该用例原按"第 615 分钟触及封顶"编写，验算如下：

```
第 615 分钟 → 阶梯费用 = 54.00 + (615−600) × 0.08 = 54.00 + 1.20 = 55.20
```

55.20 < 60.00，**并未触及封顶**，因此断言失败。

继续验算真正的封顶点：

```
54.00 + (m−600) × 0.08 = 60.00
(m−600) × 0.08 = 6.00
m−600 = 75
m = 675
```

**结论**：封顶点在**第 675 分钟**，而非 615 分钟。程序行为完全正确，是测试用例的预期值算错。

**修正**

将用例改为三段式，覆盖封顶前/恰好封顶/封顶后：

| 时长 | 计算 | 预期 | 实际 |
|------|------|------|------|
| 674 | 54.00 + 74×0.08 | 59.92（未封顶） | 59.92 ✅ |
| 675 | 54.00 + 75×0.08 | 60.00（恰好触及） | 60.00 ✅ |
| 676 | 54.00 + 76×0.08 = 60.08 | 60.00（封顶生效） | 60.00 ✅ |

**复核手段**：为避免再次凭心算失误，另用独立脚本按业务规则重算了 23 组费用数据，
逐一比对后确认全部一致，才提交修正。

### 5.4 TCX-02 分析：库存边界用例数据错误

**现象**

```
TC-IT-06 stockBoundary[3] 失败：expected: <0> but was: <5>
TC-IT-06 stockBoundary[4] 失败：expected: <0> but was: <19>
```

**分析**

原用例无论租借多少个，都断言"剩余库存 = 0"，但数据中包含租借 5 个（容量 10）
和租借 1 个（容量 20）两种部分租借场景，此时剩余库存分别为 5 和 19，程序行为正确。

**修正**

改为显式给出预期剩余库存，并补充"库存耗尽后再租必须失败"的断言：

| 容量 | 租借 | 预期剩余 |
|------|------|---------|
| 10 | 10 | 0（刚好租满） |
| 100 | 100 | 0（容量上界） |
| 10 | 9 | 1 |
| 10 | 5 | 5 |
| 20 | 1 | 19 |
| 20 | 20 | 0 |

### 5.5 TCX-03 分析：等级分布用例预期人数错误

**现象**：`TC-IT-07 reportLevelDistribution 失败`

**分析**：用例注释写"注册 4 个不同等级的会员"，但实际在 `setUp()` 中已存在张三，
又注册甲/乙/丙 3 人，共 4 人；断言却按"NORMAL 有 2 人、总数 5"编写，多算了 1 人。

**修正**：改为断言 NORMAL=1（仅张三）、其余各 1 人、总数 4，并增加"等级分布应覆盖全部 4 个等级"的断言。

### 5.6 DEF-01 分析与修正：空输入导致功能不可用

| 项目 | 内容 |
|------|------|
| **发现阶段** | 交互式手工验证阶段（补充执行边界测试后的端到端检查） |
| **缺陷类型** | 健壮性缺陷 / 提示语与实现不一致 |
| **严重程度** | 严重 —— 阻断充值、租借、修改信用分三个主流程 |
| **修改前版本** | `docs/before-fix/Main-readLong.java.txt` |

**现象描述**

菜单 3（充值）、5（租借）、7（修改信用分）的提示语均为：

```
会员号（直接回车用当前登录会员）：
```

但用户按提示直接回车时，程序却输出：

```
输入不是合法的整数。
输入无效，已取消。
```

提示语承诺的行为与实际行为矛盾，用户按提示操作必然失败。

**实际执行记录**

```
--- 会员充值 ---
会员号（直接回车用当前登录会员）：输入不是合法的整数。
输入无效，已取消。
```

**根因分析**

```java
// 修改前
private Long readLong(String prompt) {
    String line = readLine(prompt);
    if (line == null) {
        return null;          // 只处理了 EOF
    }
    try {
        return Long.parseLong(line.trim());   // ← 空串在此抛出 NumberFormatException
    } catch (NumberFormatException e) {
        System.out.println("输入不是合法的整数。");
        return null;
    }
}
```

`readLong()` 只处理了 `null`（EOF）的情况，**缺少对空串的分支处理**。
用户直接回车时 `line = ""`，`"".trim()` 仍为 `""`，而 `Long.parseLong("")`
必定抛出 `NumberFormatException`，于是走到 catch 分支输出"输入不是合法的整数"。

这也正是健壮边界值法强调的典型问题——**有效输入的分支都覆盖到了，
却漏掉了"空输入"这一既非有效也非典型无效的边界情形**。

**修正方案**

新增 `readMemberId(String prompt)` 方法，显式处理空输入：

```java
// 修改后
private Long readMemberId(String prompt) {
    String line = readLine(prompt);
    if (line == null) {
        return null;                    // EOF：取消操作
    }
    String trimmed = line.trim();
    if (trimmed.isEmpty()) {
        return -1L;                     // 空输入：使用当前登录会员
    }
    try {
        return Long.parseLong(trimmed);
    } catch (NumberFormatException e) {
        System.out.println("输入不是合法的整数。");
        return null;
    }
}
```

并将菜单 3/5/7 三处调用点由 `readLong()` 改为 `readMemberId()`。

**修改前后对比验证**

`docs/before-fix/Main-readLong.java.txt` 提供了可独立运行的对比程序：

```
=== DEF-01 修复验证 ===
输入：空串（模拟用户直接回车）
修改前返回值：输入不是合法的整数。
null   → 提示语「直接回车」功能失效
修改后返回值：-1   → -1 表示使用当前登录会员，功能正常
```

### 7.2 设计心得

**（1）缺陷往往不在"计算"里，而在"分支"里**

本次发现的 DEF-01 纯粹是分支遗漏：所有有效输入的处理都正确，
唯独漏掉了"空输入"这一分支。这印证了健壮边界值法的价值——
它主动构造无效输入，把开发者"想当然认为不会发生"的情形逼出来。
如果只做正常边界值测试，这个缺陷会一直潜伏到用户实际使用时才暴露。

**（2）测试失败不等于程序有错**

首轮 4 个失败中有 3 个是测试用例自己算错了。这带来两点体会：
一是编写预期值时不能凭心算，涉及分层计算时应独立验算（本次借助脚本复核了 23 组数据）；
二是看到失败要先问"是程序错了还是我错了"，这本身就是测试工作的重要部分。

**（3）边界值分析要求先理解业务语义**

设计用例前必须先算清"边界在哪"。例如费用封顶 60 元这条规则，
封顶点落在第 675 分钟还是 615 分钟，完全取决于第二阶梯单价 0.08 的具体取值。
不把规则算透，用例就无从设计；规则算错，用例就必然失败。

**（4）边界测试不是万能的**

边界值分析擅长发现"边界附近的计算错误和分支遗漏"，
但不擅长发现"中间值全错"或"路径组合遗漏"。
本实验的积分测试补充了跨模块路径验证，
后续实验可引入等价类划分、判定表、因果图等方法，形成互补。

**（5）常量集中是系统可维护的关键**

本系统把年龄上下界、费率、封顶金额、优惠券门槛等全部提取为
`public static final` 常量，使得业务规则一目了然、测试点易于穷举。
修改任一常量，测试用例会立即暴露规则变化带来的差异，便于回归验证——
这正是实验任务书"能在后续实验中持续复用"的要求。
